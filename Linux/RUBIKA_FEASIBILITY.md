# امکان‌سنجی روبیکا به‌عنوان storage backend

تاریخ: 2026-10-17. **نتیجه: از نظر API قابل آزمایش؛ برای دیسک اصلی رایگان و دائمی یا دانلود عمومی گسترده تأیید نشده است.** پیاده‌سازی اصلی پروژه نباید منتظر روبیکا بماند.

## ۱. شواهد رسمی

API بات با پایه `https://botapi.rubika.ir/v3/{token}/{method}` معرفی شده است. workflow مستند: `requestSendFile(type)` -> `upload_url` -> آپلود multipart در فیلد `file` -> دریافت `file_id` -> ارسال از طریق `sendFile` و بازیابی `download_url` با `getFile(file_id)`. جزئیات پاسخ و خطا باید با حساب مجاز contract-test شوند؛ از نام متدهای کتابخانه‌های غیررسمی قرارداد رسمی نسازید. [S18–S19](SOURCES.md)

این سند بین **Bot API رسمی** و کتابخانه‌های متصل به session حساب شخصی تمایز می‌گذارد. قابلیت‌های یکی، سقف‌ها یا مجوز دیگری را اثبات نمی‌کند.

## ۳. ریسک قرارداد و مجوز نرم‌افزار

قوانین رسمی حق حذف محتوا/توقف خدمات را محفوظ می‌داند و دسترسی خارج اپ به API خصوصی را منع می‌کند. بنابراین مسیر پژوهش، بات رسمی و اخذ توضیح اپراتور است؛ کتابخانه session شخصی انتخاب پیش‌فرض نیست. حق استفاده از نرم‌افزارهای متن‌باز نیز باید با حق بازنشر باینری، source obligations و مجوزهای شخص ثالث تطبیق داده شود. این تحلیل جای مشاوره حقوقی درباره قرارداد خاص را نمی‌گیرد. [S20](SOURCES.md)

فایل به‌صورت document خام فرستاده شود، نه محتوای رسانه‌ای قابل transcoding. پس از دریافت باید اندازه و SHA-256 دقیقاً برابر اصل باشد. کوچک‌ترین تغییر، backend را برای آن نوع artifact مردود می‌کند. بیت‌های یک `.deb` را نمی‌توان مانند ویدیو بازفشرده‌سازی کرد.

## ۵. طرح آداپتور

Interface در [API_CONTRACT.md](API_CONTRACT.md) تعریف شده است. نگاشت خصوصی: `sha256 -> file_id + size + upload_time + verification_time + backend_account_alias`. نام alias حاوی شماره تلفن نباشد. Token و session در secret mount؛ هیچ‌کدام در YAML عمومی، خط فرمان نمایان یا Git قرار نگیرند.

`download_target` باید در لحظه URL تازه درخواست کند، scheme/host/DNS/CDN chain را مطابق allowlist بازبینی کند، TTL محافظه‌کارانه را رعایت کند و queryهای bearer را در لاگ حذف کند. API availability جدا از object availability پایش شود. اگر API خارجی/غیرقابل دسترس شود، URLهای قدیمی را بی‌دلیل دائمی فرض نکنید.

کاربر هرگز از gateway آدرس دلخواه برای upload یا fetch نمی‌فرستد. upload فقط برای artifact ثبت‌شده، دارای مجوز و hash معلوم توسط worker مدیر انجام می‌شود. حساب دوم ابزار افزایش مجاز تاب‌آوری نیست مگر قرارداد و واقعیت failure domain آن روشن شود.

## ۶. آزمون کم‌خطر و قابل تکرار

ابتدا با bot متعلق به مالک پروژه و فایل‌های مصنوعی ۱MiB، ۸MiB و ۶۴MiB کار کنید. هزینه/سهمیه را پیش از فایل بزرگ بررسی کنید. برای هر round-trip نام test، زمان UTC، اندازه، SHA-256، وضعیت API و metadata فایل ثبت شود؛ credentials و URL خصوصی در خروجی عمومی حذف شوند.

سه مسیر سنجیده شود: دانلود از میزبان uploader؛ client ناشناس دوم؛ client روی ISP دیگر داخل ایران. هر بار full hash و حجم کنترل شود. سپس GET Range و resume با byte offsets معلوم؛ پاسخ 200 به Range را پشتیبانی resume ننامید. ۲۴/۷۲ساعت ماندگاری زمان واقعی می‌خواهد؛ این نشست آن را اجرا نکرده و گزارش نمی‌کند.

شبیه‌سازی قطعی فقط در ماشین/namespace آزمایشی مجاز انجام شود؛ اتصال مدیریتی یا مسیر production کاربر قطع نشود. دامنه API، upload و CDN فایل ممکن است متفاوت باشند؛ هرکدام باید در allowlist مبتنی بر شواهد ثبت شوند. اگر یک حلقه خارجی لازم است، قابلیت offline مردود/محدود ثبت شود.

## ۷. تصمیم go/no-go

برای **آزمایشی**: API رسمی کار کند، full digest برابر باشد و هزینه/مجوز قابل قبول باشد. برای **backend عمومی**: دسترسی ناشناس، رفتار TTL، Range، سهمیه، قرارداد، چند ISP و recovery مستقل نیز باید قبول شوند. برای **تنها کپی حیاتی**: در این معماری مجاز نیست، حتی پس از تست اولیه.

تقسیم فایل بزرگ به قطعات راه‌حل شفاف برای APT/ISO client نیست. client معمولی باید یک stream و Range صحیح ببیند؛ reassembly به proxy، state و ترافیک gateway نیاز دارد. این قابلیت P0 نیست. فایل بزرگ‌تر از سقف تأییدشده را به storage استاندارد/میرور مناسب بسپارید.

**خروجی عملی اکنون:** `RubikaBackend` غیرفعال با خطای صریح قابلیت، و Local CAS فعال. هیچ test token، حساب یا فایل واقعی روی روبیکا در این پژوهش ایجاد نشد.
